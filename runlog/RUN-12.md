# RUN-12 handoff — Phone: installable web app and push

**Branch:** `run/12-phone` · **Head:** `d01a4b3` · **Status:** awaiting verification

## Built
- `src/ui/public/manifest.webmanifest` and three PNG icons (192, 512, and a maskable 512 with the content inside the 80% safe circle, so iOS does not crop the mark). Generated by a script with no image dependency, committed as bytes.
- `src/ui/public/sw.js` — the shell worker. Network first for the app's own files so a running workbench always serves the current build; the cache is what an offline phone falls back to. `/api/` is never cached. It also handles `push` and `notificationclick`, reusing an open window when there is one, because the token lives in that page's memory and nowhere else.
- `src/runtime/push/vapid.ts` — the keys, generated once at `init` into `data/vapid.json` at 0600, registered with the redactor, never rotated.
- `src/runtime/push/store.ts` + migration `0008` — subscriptions per device with the kinds each one wants, dispatch, and the `404`/`410` handling that stops retrying a phone that threw the subscription away.
- Routes: `GET /push/vapid-public-key`, `GET /push/subscriptions`, `POST /push/subscribe`, `PUT /push/subscriptions/:id`, `DELETE /push/subscriptions/:id`.
- `src/runtime/engine/run.ts` — the four moments: `approval-requested`, a blocking `review-requested`, `run-failed`, and the completion of a run the scheduler started. A push that fails never fails the run it is about.
- `src/ui/lib/push.ts`, `src/ui/components/PushSettings.tsx` — subscribing from the browser, with the per-device per-kind toggles, degrading to a sentence rather than a broken switch where push is not available.
- The phone layout: a bottom tab bar, 44px touch targets below `md`, Runs as cards, wrapping document paths.
- Migration `0009` — `approvals.ordinal`, so a batched card lists its actions in ask order.

## Not built (deliberate)
- Any offline data cache — the brief's *Do not*, and the reason the worker's `isShell` check exists.
- A native app.
- Anything in a push payload beyond ids and a fixed title.
- Tailnet exposure is *documented* (`deploy.md`, `--expose`) but cannot be verified from this build environment: there is no tailnet here. The human-verification script is where that gets checked.

## Deviations from the brief
- **DoD 4 asserts installability directly rather than through Lighthouse.** The manifest's required fields, the icon files' real IHDR dimensions, the `<link rel="manifest">`, and the worker's fetch handler are exactly what Chrome's installability check reads; running Lighthouse would add a headless-browser and network dependency to CI to learn the same four facts. Stated here rather than quietly.
- **The touch-target check measures the DOM.** Asserting a class name would have proved nothing; measuring found the network banner's 24px switch, which no amount of reading the classes would have.
- **`ordinal` on approvals** — a RUN-06 fix that belongs here because this run found it.

## Bugs found by the tests
- **A batched approval card's order was luck.** ULIDs are not monotonic within a millisecond unless a monotonic factory makes them, and parallel tool calls land in the same millisecond. Recorded explicitly now.
- **The network banner's switch was a 24px target**, found by measuring rather than by reading.
- **The Library's document table pushed the page sideways** on a phone as soon as a run had filed a document with a long path.

## Human verification script

The phone has only been seen at an iPhone viewport in Chromium. Safari delivers Web Push **only to a web app
installed on the Home Screen**, so this script is what actually proves it — nothing in CI can.

**Getting the workbench in front of the phone.** It binds to `127.0.0.1` and is never exposed to the internet.
Either follow `deploy.md` §2–3 (Tailscale on the host, `tailscale serve`, and `--expose <hostname>`), or, on a
trusted home network, start it with `--bind 0.0.0.0 --expose <your-machine-name>.local` and reach it from the
phone on the same Wi-Fi. Push needs a secure context, so a plain `http://` LAN address will install but will
**not** offer notifications; `tailscale serve` gives you the TLS the phone requires.

1. Open the tokened URL in **Safari** on the iPhone. Expect the phone layout: a bottom tab bar, Runs as cards,
   and touch targets you can hit without aiming.
2. Share → **Add to Home Screen**. Open it from the Home Screen. Expect no Safari chrome, and expect it to
   still be signed in — the token lives in that page, so if it asks again, that is the finding.
3. In the installed app: **Settings → Notifications**. Expect per-kind toggles for the four moments. Turn on
   *approval requested* and *needs review*. Expect iOS to ask for permission at that moment, not at load.
4. From your laptop, start a run that parks for an approval. Expect a notification on the phone within a few
   seconds.
5. Tap it. Expect it to open the installed app **on the approval**, not on the Dashboard, and to reuse the
   already-open window rather than starting a second one.
6. Approve from the phone. Expect the run to continue, and expect the laptop's Dashboard to update without a
   reload.
7. Read the notification itself: it should name the run and what it wants, and carry **no prompt text, no model
   output and no document content** (SEC-32). A push goes through a third party; it carries ids, not your work.
8. Repeat for *run failed* and for a scheduled run completing. Then turn one kind off and confirm that kind
   stops arriving while the others still do — the toggles are per device and per kind.
9. Delete the app from the Home Screen and reinstall it. Expect the old subscription to stop being retried
   rather than to keep erroring: the phone threw the subscription away, and a `404`/`410` is how it says so.
10. Offline behaviour, deliberately limited: turn on Airplane Mode and open the app. Expect the shell to load
    from cache and expect it to say it cannot reach the runtime. It must **not** show you stale runs — no
    workspace data is cached, on purpose.
